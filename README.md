# 跳一跳 屏幕识别自动脚本（自适应版）

在 Windows 上截取微信小游戏「跳一跳」窗口画面，用 OpenCV 识别棋子与目标方块，
模拟鼠标按住蓄力完成自动跳跃。当前配置按压系数固定为 k=2.61，在线自适应关闭。

## 等价计算与交付清理（v1.3-rc.3）

- 将皮肤收腰核验的重复逐行中位数计算向量化，复用 Lab 色差数组；采样窗口、
  数值类型、判定阈值及歧义处理不变。不调整 k、gamma、瞄准和鼠标/暂停控制。
- 冻结软件面板把运行日志放在 EXE 旁的 debug 目录，不再写入内部资源目录。
  ZIP 和安装包均明确排除根目录及 `_internal` 下的 logs/debug 运行数据；
  其它依赖的合法同名资源不做全局删除。
- 本次只做无输入软件验证，不恢复已停止的 10 分钟跟进，不自动启动游戏测试。
  性能观察、最终源码/构建身份及未完成实机项目以 Release 的测试汇总为准。

## 日常不限跳数与状态栏时钟（2026-10-11，本地候选）

- 日常长跑、CPU 入口及安装快捷方式使用 `--max-jumps 0 --daemon`，0 表示不限跳数；
  新默认配置也是 0，升级时即使保留旧配置中的 5000，正常快捷方式也会明确覆盖。
  面板显示“本轮跳数：N（不限）”，不再显示 `/5000`。F8 / q / Esc / Ctrl+C、安全
  停止和已有运行时间保护仍有效；取消跳数上限不代表忽略故障或无限运行时间。
- 面板默认每 0.25 秒重绘，运行时长用单调时钟在两跳之间独立推进；暂停、恢复准备
  和停止时冻结。不增加游戏识别、磁盘心跳或鼠标输入频率，跳数/命中统计只在实际
  完成并判定一跳后变化。状态有效时不再重复扫描/解析 CSV；旧格式状态文件保持兼容。
- 有限次数只用于独立临时测试：`tools/run_frozen_acceptance.py --execute-live --exe
  <新EXE> --out <新证据目录> --jumps 500`（也可指定 1000/2000）。测试驱动临时覆盖
  `--max-jumps N`，不修改日常配置或快捷方式；`run_skin_acceptance.py` 仍按门禁逐轮运行。
- 当前运行进程不能热替换。构建保存到独立目录，更新桌面入口后，下次启动才生效；
  不覆盖正在运行的软件，不自动恢复人工暂停，也不另开一个输入实例。

## 自动皮肤适配（v1.3-rc.2 候选）

- 默认自动识别初始紫色、金色以及圆头/收腰身体轮廓的其它颜色，无需选择颜色、重新
  校准按压系数或修改 HSV 配置。旧配置缺少 `piece_skin_shape_enabled` 也默认启用。
- 初始人物保留已验证的颜色/模板快路径；颜色候选不可信时自动检查完整头身几何、
  头身材质一致性、平台支撑和唯一性。弱紫色干扰物不再阻断金色人物适配。
- 每帧重新验证，不保存过期的颜色画像；换色、镜头移动和暂停恢复不会锁定旧皮肤。
  人物掩码覆盖头身，防止把金色头部当作目标；面板显示当前识别路径。
- 金色闪烁纹理使边缘轮廓断裂时，从当前圆头内部自动采集 Lab 材质色，局部重建
  身体轮廓；仍经过完整头身、收腰、支撑和唯一性核验，不降低几何安全阈值。
  色块连到同色平台或触及采样区边界时拒绝，颜色画像不跨帧/暂停持久保存。
  头部采样同时估计色度离散度，排除绿色平台阴影等相近亮度、不同材质的干扰。
- 金色人物站在白色书本上的实机停帧暴露圆头边缘被闪烁纹理切断的问题。现在从
  近圆边缘片段的内部材质生成完整圆头候选；只有完整候选再次通过原宽高比、
  圆度、完整性及头身/平台支撑核验才接受。不是放宽头部阈值，也不是金色色相特例。
- 金色闪烁材质生成身体内部片段时，只有已通过全部人物核验、共享同一圆头且小轮廓
  完全内嵌并被大轮廓覆盖至少 95% 的候选才合并；保留完整身体的脚底。不同圆头、
  非内嵌身体或缺失轮廓仍视为歧义并拒绝，不依赖金色色相或上一次的位置。
- 身体材质轮廓增加按当前已验证圆头尺寸限制的微小边界补洞提案，
  标准 553px 宽画面上限为 7px，缩放时上限等比例变化且仍受头径限制；
  保留原提案，并重新通过原完整性、收腰、材质、台面支撑和唯一性核验。
  连到同色台面或被截断的轮廓仍拒绝，不通过降低完整性阈值维持跳跃。
  独立纹理区域候选同样使用此有界补洞规则，同时保留原候选；不直接填凸包，
  不补大段缺失身体，完整性与平台/边界/歧义核验仍使用原门槛。
  补洞在原连通区域内独立进行，不把邻近纸箱接缝合并进人物，也不延长原区域的脚点。
  纹理补洞仅在同一圆头没有通过全部核验的原候选时兜底，不能覆盖可靠的原脚点；
  不同圆头仍分别验证，以保留多个人物时的歧义拒绝。
- 金色与黄色台面相近时，用当前头部闪烁像素覆盖率生成局部纹理区域提案，减少
  单个亮点掩码之间的空隙；色距、圆头、身体完整性、收腰、支撑与边界核验仍不变。
  纹理不跨帧保存，平滑台面/细接缝不能凭纹理直接当作人物。
- 阴影把闪烁纹理量化到很小的亮度差时，联合 Lab 三通道的细纹理密度提出身体轮廓；
  要求当前圆头内至少 60% 像素具有细纹理，再通过原身体完整性与全部支撑核验。
  不降低完整性/颜色安全阈值，也不把低对比截图中的猜测当作已落地。
- 窄台面边缘与人物边缘连成闭合轮廓时，另外核对按圆头尺寸采样的脚部材质。
  只有脚部同时出现超出原 Lab 色距和当前头部色度离散度的异材质证据才拒绝；
  单纯亮度阴影不会被当作另一种材质。不扩大平台支撑范围，也不合并歧义人物。
- 同色纸箱上的金色人物增加当前头部纹理采样，区分闪烁身体与平滑台面；仍核对
  收腰、完整轮廓与平台支撑。不可信 HSV 色块和仅 RGB 相似的杯子不再作为人物兜底，
  真实人物横躺或丢失时安全停下，不继续用杯子位置发起跳跃。
- OpenCL 的设备枚举/预热增加禁输入子进程预检；异常退出或超时会跳过 OpenCL，
  保留 CUDA/CPU 回退。预检通过后计算仍在主进程，不能声称所有驱动调用都已隔离。
- 支持范围不是“所有皮肤”：饰品改变轮廓、白色与白台面重合、遮挡、横躺或多个人物
  候选时可能安全停止，不通过盲跳或降低校验门槛维持运行。识别成功不等于命中率已验收。
- 多轮实机工具 `tools/run_skin_acceptance.py --execute-live --exe <新EXE> --out <新目录>`
  顺序运行 500 SIMD、1000 auto、2000 GPU；单轮失败、F8/停止请求即终止后续轮次。
  人工暂停不会被协调器恢复。只在新冻结版本通过校验后使用，不用旧安装版替代。
- 实机统计、置信区间、未完成项和最终源码身份以该版本 Release 的 `TEST_SUMMARY.md`
  为准；本节说明功能，不预先宣称金色皮肤达到初始人物的命中率。

## Windows 暂停与手动启动（2026-10-08，待发布）

本节是当前源码的新行为；旧的 1.1 安装包尚不包含暂停功能，不能用旧包代替本次验收。

- 普通/daemon 启动先等待用户手动打开「跳一跳」，不搜索微信、不代开小程序。
  默认无限等待；发现窗口后倒计时 3 秒。离线识别和 `--selftest` 不等待游戏。
- Alt+P 全局切换暂停/恢复，控制台 P 也可切换；F8、q、Esc、Ctrl+C 保持停止用途。
  等面板显示「已暂停」再切换应用。已有按压会正常释放，当前跳有界核对后暂停。
- 已暂停时不切前台、不调整窗口、不抓帧识别、不自动重开，只保留低频心跳。
  再按 Alt+P 才恢复：重新找窗口、倒计时、清除旧目标与位置先验、同步分数。
  暂停时间和恢复准备不计入运行上限或看门狗；人工操作不计为脚本命中。
- 注册热键失败时明确报错并保持暂停，不会静默开跑。可在控制台按 P 明确继续，
  或通过 `--pause-hotkey Alt+Shift+P` 修改热键后重启。热键不能与停止键冲突。
- 原生按下与暂停/停止请求在同一控制锁上提交，防止最后一次检查后仍偷偷按下。
  前后台输入共用按压/释放逻辑，原生调用异常或中断也尝试释放，不持锁等待蓄力。
- 当前跳的已知落地/死亡先写入日志和统计，再尝试重开；暂停取消重开不丢失或重复当前跳。

配置/CLI：`pause_hotkey="Alt+P"` / `--pause-hotkey`；
`startup_wait_s=0` / `--startup-wait-s`（0 无限）；
`start_delay_s=3` / `--start-delay-s`。缺字段的旧配置使用这些默认值。
面板显示等待、倒计时、准备暂停、已暂停、恢复中、有效热键和累计暂停时间，
并显示累计及最近 100 跳的 HUD 判定统计和覆盖率。

2026-10-08 新驱动核验：RTX 3070 Ti Laptop / NVIDIA 617.42 / CuPy 14.2.0，
驱动 API 报 CUDA 13.4，实际加载运行时为 CUDA 12.9。真实 CUDA 三轮各处理
500/1000/2000 张合成帧，全部与 SIMD 零像素差异，活跃设备内存始终 2,909,696 字节，
均值约 3.37/3.34/3.48ms。源码和既有完整 1.1 冻结软件的实际 GPU/OpenCL 自检通过。
515 张历史帧、35 组合边界、NVIDIA/Intel 全颜色 HSV 一致性和故障回退检查通过。
这些证明当前机器驱动兼容，不代表其它驱动、AMD 硬件或实机命中率已通过。

无输入检查：`python -m unittest discover -s tests -v`；
`python tools/check_cuda_driver.py --out build/cuda-driver-check.json`；
`python tools/regress.py`；`python tools/replay_test.py`。
控制测试包括 3500 跳模拟长跑与可控时钟长暂停，另有 Windows 原生热键注册、
冲突、清理和本线程消息投递测试。原生消息投递不是物理长按测试。

实机验收记录器 `tools/live_acceptance.py` 仅显式 `--execute-live` 才允许输入，
沿用主程序的闭环识别/输入逻辑，不代开小程序。它记录鼠标/前台调用，
每 50 跳通过自己的热键监听线程请求暂停（首个暂停 95 秒，其余 3 秒），

## 跨设备加速与兼容版本（2026-10-07 续接）

当前正式链路包含 **NumPy CPU / 优化 OpenCV SIMD / CuPy CUDA / PyOpenCL**。
OpenCL 内核只使用 OpenCL 1.2 的整数功能，不要求 fp64 或厂商扩展，可在具备相应驱动的
AMD、Intel、NVIDIA GPU 上尝试运行。实际验证设备为 RTX 3070 Ti Laptop 和 Intel Iris Xe；
本机没有 AMD GPU，不能声称已在 AMD 硬件验收。程序仍面向 Windows x64。

`auto` 会测量 CPU、CUDA、OpenCL 的端到端耗时并核对输出：加速器必须至少快 1.5 倍才采用。
多张 OpenCL GPU 也会逐张核对并实测选择，支持 `opencl_device` 名称/厂商子串过滤。
每 300 帧复测；运行时退化或失败会回退 CPU。驱动首次编译在禁输入子进程中预检，
失败或 20 秒超时会跳过该设备。未安装可选库、没有显卡驱动、没有匹配设备也可用 CPU。
自检计时和面板状态区分实际后端与回退，不把 CPU 回退误报成 GPU 成功。

CPU SIMD 新路径将 HSV 拆为连续通道，减少 cv2 对跨步子视图的隐式复制；

```

  = 按压 570ms + 抓帧识别 135ms + 落地等待 1238ms + 读分 1ms
```

关键修正：**落地等待的 1238ms 主要是游戏自己的跳跃动画时长**，不是我们的轮询开销。
`replay_test` 里 `wait_landing` 中位 230ms 是"画面已落定后检测所需时间"，两者口径不同，
不能混为一谈（把 230ms 当成实机落地耗时是错的）。每跳 2s 基本由游戏节奏决定，
我们可压缩的只剩抓帧识别那 135ms。

手段：轮询间隔 50/60/250ms 收到 **30/40/100ms**；窗口解析每 5 次一次（省 ~12ms/跳）；
进程 AboveNormal、面板 BelowNormal（面板绝不跟 bot 抢 CPU）；OpenCV 固定 4 线程
（实测比 20 线程快 1~2.4ms/次）。

### 窗口尺寸守卫：尺寸一变就会"识别不了"，现在自动调回

识别里所有**绝对像素**阈值（中心白点面积 14~260、最小方块宽 120px、落点安定容差 3px…）
都按 **553×1050** 的客户区标定。窗口被拖动缩放后，最直接的症状是**「开始游戏」按钮的

现在脚本会自己做尺寸守卫（`window_size_policy`，默认 `auto`）：

## 工作原理

1. `SetProcessDpiAwareness` 后按窗口标题 `^跳一跳$` + 进程名 `WeChatAppEx` 定位窗口，
   每轮重新读取客户区，支持窗口移动/缩放。
2. 逐行估计背景颜色，按“比背景更暗 / 色相不同 / 近纯白”三类偏离分割出方块；
   棋子用「深蓝紫色 + 高饱和 + 低亮度」掩码提取，取包围盒底边中点作为落脚锚点。
3. 目标方块取“顶角 + 左右对称性/宽度平台期”估计顶面中心（可处理相邻方块粘连、
   白色方块、彩色方块），距离 `d` = 锚点到顶面中心的像素距离，按压时长 `t = k·d`。
4. 落地判定要求：连续 3 帧画面稳定 + 棋子位置不动 + 脚下确实有方块
   （避免把“正在坠落”误判成已落地）。
5. 落点误差 = 落地后棋子锚点相对脚下方块顶面中心在跳跃方向上的偏移，
   用指数平滑后的误差在线修正 `k`（单步 ≤5%，限幅 ±15%）。
6. 死亡（超时未落地）后自动点「再玩一局」重开；连续 3 次死亡回退历史最优 k；
   开始界面 / 结算界面用按钮模板匹配（`templates/ui_*.png`）识别，避免空按。
7. 每跳写一行 CSV 到 `logs\run_*.csv`（序号、距离、按压时长、误差、结果、备注）。

## 读分与命中率判定（已打通，这是权威指标）

`templates/digit_0..9.png` 已生成，`read_score()` 在人工核对过的样本上 **19/19 完全正确**。
由此得到一条**权威的命中判定链路**：

1. 每跳读 HUD 分数 → `delta = score_now − score_prev`
2. **得分规律（本轮实测确认）**：
   - 普通落点：`delta == 1`
   - 命中中心且未封顶：`delta == 2 × 连击数`
   - 命中中心且已封顶：`delta == 32`（**连击加成 +32 封顶**，封顶后每跳仍 +32）
   - 礼盒/音乐盒等额外加分 → 叠加在上述基础上
3. 抗级联处理：`delta<=0`（HUD 未刷新）会重读一次；读数异常或含礼盒加分时**不重置连击**，
   避免一次误读导致后续全部错判；偶数增量可反推连击数重新同步。

**读分器可靠性**：对全部 11 个历史轮次共 **243 帧**跑读分，**243/243 全部读出、零跳变**
（序列单调性检查通过），这是所有命中率统计的基础。

**命中率演进**（同一判据、全部历史轮次）：

| 阶段 | 各轮命中率 |
| --- | --- |
| 顶面中心/目标选择修复前 | 16% / 43% / 32% / 36% / 33% |
| **修复后** | 32% / **79%** / **97.3%** / 70% |

最近三轮分别为 79%、97.3%、70.4%；单轮最长连续命中链 **16 次**，
单轮最高游戏得分 **18331**。

> 关键教训：`|落点误差|` 这条判据**不可靠**（与真实命中几乎不相关，误差约 ±30px，
> 因为它同时受棋子阴影、方块粘连、屏幕裁切影响）。它现在只作为诊断量保留，
> **一切命中率/调参结论以分数判定为准**。

**2026-10-01 量化复核（三轮共 3457 个落地样本）**：把每跳的 `|落点误差|` 与真实分数
判据并排比较，两者几乎无关联：

| 真值分组 | 样本 | `|err|` 中位 | `|err|` 均值 | `|err|<12px` 占比 |
| --- | --- | --- | --- | --- |
| 命中中心 | 1944 | 22.5px | 23.7px | 18.5% |
| 普通落点 | 47 | 20.2px | 24.4px | 27.7% |

也就是说：**真实命中中心的跳里，只有 18.5% 的 `|err|` 小于 12px**，而真实没命中的跳里
反而有 27.7% "看起来"很小。落点误差的测量噪声（σ≈28px）**远大于**真实落点散布
（否则不可能有 97.6% 的中心命中率），所以：

- 任何用它做的 k 自适应、传递函数拟合（`L = a·t + c`）、距离分桶微调**都是无效的**，
  拟合出来的 a/c 只是在拟合测量噪声本身。`gamma` 保持 0，k 冻结在 2.61。
- 唯一权威信号是 HUD 分数增量。所有精度结论都从它来。

**用真值看精度分布**（三轮 3457 样本，按目标距离分桶）：

| 目标距离 | 样本 | 真实命中率 |
| --- | --- | --- |
| 80–120px | 285 | 99.3% |
| 120–200px | 982 | 97.6% |
| 200–280px | 1064 | 98.3% |
| 280–360px | 968 | 99.0% |
| **360–400px** | 129 | **80.6%** ← 明显短板 |

按按压时长看同样只有长按段偏低（900–1000ms：90.8%，其余各段 96%~99%）。
中短距离已经接近上限，**下一步精度工作的靶子是远距离（>360px / >900ms）**。
为此已加埋点：CSV 备注里记录目标方块几何（`tb=x,y,w,h tw=顶宽`），
并且**真实未命中时自动存 `debug/miss/miss_*_before.png / _after.png`**，
用于逐例判断远距离失手是"目标中心估偏"还是"按压传递非线性"。

**两种落点误差测量的实战对比（`tools/measure_compare.py`，2026-10-01）**：
拿 15 组**真实未命中**的起跳帧+落地帧当测试集，看哪种测量能认出"这跳没中"：

| 测量法 | 把真实未命中误判成"命中"的比例 | 备注 |
| --- | --- | --- |
| 掩码法（CSV 当前使用） | 13%（2/15） | 噪声 σ≈28px |
| 相位相关法（`landing_method=flow`） | 7%（1/15） | 但会给出 -178 / -361px 的**灾难性离群值**（镜头平移估错），单独用不可信 |

结论：**两种测量都不足以驱动调参**，`gamma` 继续为 0，`k` 继续冻结在 2.61。
要真正解决远距离精度，需要能"看见"游戏自带的中心标记（唱片机转盘中心的白点、
便利店屋顶的圆点）并据此标定顶面中心估计，这是下一步的研究项，不是调参能解决的。

**远程精度现状（第 4 轮 1933 个有效样本）**：长跳是唯一明显短板，且已量化——

| 目标距离 | 样本 | 真实命中率 |
| --- | --- | --- |
| 50–150px | 440 | 97.5% |
| 150–300px | 1002 | 99.2% |
| 300–350px | 304 | 99.3% |
| **350–400px** | **171** | **88.9%** |

长跳（>350px）里还有一个子模式：**顶面估计宽度 / 连通域宽度 < 0.45 的候选，未命中率 71%
（5/7）**，而 ≥0.6 的只有 9%。曾尝试把"退化估计"门限从 0.10 提到 0.45 来回避这类候选，
**回退**了：A/B 显示它会把真目标（白圆柱，比值 0.38）也降级，兜底随即选中棋子脚下的
方块（比值 0.03、距离只有 42px），反而更糟。说明"低比值"是"这一帧难估"的**症状**，
不是能用候选替换解决的**病**；下一步要改的是顶面中心估计本身（例如识别抬高的唱片/
圆台顶面，或直接检测游戏自带的中心白点）。

**中心标记检测（已实现，默认按窄门限启用）**：游戏会给一部分方块画一个亮白小圆点
（唱片机转盘中心、快递箱、便利店屋顶），它就是真正的中心判定点。`find_center_dot()`
在估计中心周围 90px 内找"够亮(V≥238)、够白(S≤14)、面积 14~260、近似圆、比紧邻一圈
亮 ≥12 灰度"的连通域，用它替代顶面估计中心。三个实测案例：

| 现场 | 顶面估计 | 白点实测 | 偏差 |
| --- | --- | --- | --- |
| 唱片机 `miss_..._034003` | (456,453) | (456,469) | 16px |
| 唱片机 `miss_..._051616` | (445,427) | (445,475) | **48px** |
| 唱片机 `miss_..._032322` | (392,499) | (403,500) | 11px |

但这个检测器在全量帧上会误锁**小方块上的白色高光**（实测咖啡杯杯壁高光把瞄点拉偏
67px），所以加了窄门限：只在 `顶面宽度 < 0.20×连通域宽度` **且** `连通域宽度 ≥200px`
时启用（正是"顶面估计明显不可信的大方块"）。窄门限下全量 572 帧 A/B **零影响**，
只在那类退化估计上生效——属于"只修错、不改对"的改法。

### 中心白点当"真值尺子"：量化出系统性过冲（2026-10-01 07:00）

把 `tools/landing_truth.py` 用到 148 组真实未命中的 起跳/落地 帧上：在**落地帧**里
找游戏自带的中心白点，直接量"棋子锚点相对真中心的偏移"，得到不依赖掩码估计的**真实误差**：

| 指标 | 掩码法（CSV 里的 error_px） | 白点真值 |
| --- | --- | --- |
| 均值 | −2.3px | **+23.0px** |
| 中位 | −4.0px | **+20.5px** |
| 真实性 | 噪声 ±28px，符号都会反 | 直接量游戏的中心点 |

16 组里有 10 组真实 |误差| > 12px（它们本来就都是未命中样本），而且**几乎全是正号=过冲**
——即对这类"抬高台面"方块，瞄点被系统性算到了真中心**前方约 20px**。这也解释了为什么
处方块的真实命中率只有 92~97% 而"小块"有 99.5%：块越大、台面越复杂，顶面中心越容易偏。

据此把中心白点检测**从窄门限放宽到通用**（`center_dot_ratio_gate: 0.2 → 1.0`、
`center_dot_min_block_width: 200 → 120`、`center_dot_max_offset_px: 60 → 55`），
全量 572 帧 A/B：**571 帧完全一致，仅 1 个调试探针帧位移 23px**（低风险）。
两处生效：

1. **瞄点**：`find_target` 找到白点时，用它替代顶面估计中心（`Block.dot` 记录来源，
   主循环每跳只打一条日志：`#N 瞄点用中心白点校正：(x,y)`）。
2. **落地误差**：主循环在落地帧也用白点校正 `error_px`（`center_dot_landing_radius_px`）。

   > **这条已被推翻（2026-10-01 13:10）**：拿 35 个"白点量出的误差"与游戏分数对照，
   > 12 行测量值 > 40px 的跳被判为"命中中心"——落地瞬间棋子正好挡住白点，检测器抓到
   > 的多是别的高光/边界。现在白点值只写在 `err_dot_px` 列、**不再覆盖** `error_px`，
   > 且明确标注"非真值"。详见后面「落点误差的'真值'路线破产」一节。

   > 更正（2026-10-01 11:10，见下一节）：白点只覆盖 28.7% 的帧，且短距离（<120px）上
   > `error_px` 仍呈 +16px 的系统性假象。**该列目前仍不足以驱动调参**，`gamma` 保持 0。

### 精度路线图修订：瓶颈是瞄点，不是按压（2026-10-01 11:10，离线实测）

用全部历史 CSV（6680 条带 `tb=`/`tw=` 的落地样本）+ 253 张现场帧做了三组判别实验，
结论与"继续调参"相反，先把方向钉住：

**1. "粘连块命中率低"是距离混淆，不是块类别效应。**

| 距离带 | 比值<0.45 | 0.45~0.60 | ≥0.60 | 全带 |
| --- | --- | --- | --- | --- |
| 0~120px | +18.8 (n=454) | +10.8 (n=192) | +22.5 (n=11) | **+16.5 (n=657)** |
| 120~180px | +0.2 (n=767) | −1.6 (n=364) | +0.1 (n=307) | −0.3 (n=1438) |
| 180~320px | −4.1 / −3.0 | +7.7 (n=79) | −2.8 / −1.5 | −2.3 / −1.5 |
| 320px+ | +16.3 (n=21) | — | +1.3 (n=1196) | +1.6 (n=1222) |

同距离带内"比值<0.45"只比其他候选高 **+7.3px**（0~120px 带），而在 120~180px 带只差
+1.0px。更关键的是：**+16px 的测量偏差与 97.5% 的真实命中率不可能同时成立**
（±12px 判定半径下 16px 常数偏差会导致近乎全不中），所以短距离上的 `error_px`
仍是**测量假象**——棋子贴邻时"最宽连续段"会锁到上一块/相邻块。
→ 结论：`low_ratio_trim_ratio` 的 A/B **不值得做**，按块类别缩短按压没有数据支撑。

**2. 白点真值只覆盖约 19% 的目标帧**（干净原始帧 586 张里 110 张能找到游戏中心白点；
注意 `Block.dot` 只在白点与估计相差 >3px 时才记录，直接统计会漏掉"估计已经很准"的帧）。
游戏只在部分方块上画中心点，剩下 **约 81% 的瞄点只能靠顶面估计**。

**3. 顶面估计对真值的误差（110 帧白点真值，关掉白点替换后逐帧比较；干净原始帧）**

| 指标 | 值 |
| --- | --- |
| 欧氏 中位 / p90 | **10.20 px / 16.11 px** |
| 沿轴 中位 / 均值 | **+3.94 px / +6.9 px** |
| \|沿轴\| 中位 / p90 | 5.31 px / 10.70 px |
| \|沿轴\| > 12px 占比 | 8.2% |

沿轴方向有**同号系统偏置**（估计值偏在真值前方）→ 这是可修的，见下一节。

**结论：精度上限由"顶面中心估计"决定，不是由 k/按压传递决定。** 在约 81% 没有白点的
目标上，瞄点沿轴中位误差 5.3px、p90 10.7px，已经接近 ±12px 的中心判定半径，
这解释了残留未命中。下一步的离线工作是**改进顶面中心估计**：以这批白点真值当验收集
（同一批帧上比较新旧估计器的误差分布），改造后再走 572 帧 A/B 闸门，而不是继续调 k/gamma。

### 瞄点几何中心：消掉沿着跳跃轴的系统偏置（2026-10-01 11:20 实现，13:00 A/B 后**默认关闭**）

**最终结论（先说）**：开关 `aim_center_mode` 已实现并保留，但**默认值改回 `estimate`**。
同码 1000 vs 1000 的实机 A/B 没有显示任何收益；而离线那套"瞄点误差减半"的证据
只覆盖有白点的帧，生产代码在这些帧上本来就用白点描准，**证据不能外推到它真正生效的
那 81% 无白点帧**。详见本节末尾的 A/B 小节。

工具：`tools/aim_error.py`（采集 + 汇总，纯离线，只读 PNG）。它把每帧的"顶面估计中心"
和"游戏自带中心白点"成对导出成 `debug/aim/dataset*.csv`。

**口径修正（重要）**：`Block.dot` 只在白点与估计相差 >3px 时才记录，直接拿它统计会
引入选择偏差、把误差算大。正确做法是用 `find_dot_near` 直接搜到的白点当真值
（数据集里的 `relaxed_*` 列），白点可用率 **14.2%（172/1209 帧）**。

**修改**：等距投影下菱形/椭圆顶面的中心行必然满足 `y = 顶角y + 0.5·顶宽·slope`
（顶角到中心行的竖直距离 = 半顶宽×斜率）。用它替换原来的"边缘拟合/等宽平台期"结果，
新增开关 `aim_center_mode`（`estimate` 默认 / `geometric` 可选）。

**验收集对比**（同一批帧、同一口径，中位/均值单位 px）：

| 数据集 | 总帧 | 白点帧 | 欧氏中位 | 欧氏 p90 | 沿轴中位 | \|沿轴\|中位 | >12px |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `estimate`（改动前） | 586 | 110 | 10.20 | 16.11 | **+3.94** | 5.31 | 8.2% |
| `geometric`（可选，默认关） | 586 | 110 | **6.83** | 16.11 | **−0.37** | **3.30** | 8.2% |

> **数据必须来自原始帧**：`debug/run_*/jump_NNN_before.png` / `_after.png` 是
> `annotate()` 画过红/绿框和十字的**标注图**（实测含 3013 个纯绿、673 个纯红像素），
> 只有 `jump_NNN_raw.png` / `_raw_after.png` 是原始帧。第一版数据集误用了标注图，
> 得出的"p90 41.66px、>12px 15.7%、白点可用率 14.2%"全部偏大，已作废；
> `tools/aim_error.py` 现在会按文件名和"纯红/纯绿像素计数"双重剔除标注图
> （本次采集 654 张里剔除 28 张）。干净数据下白点可用率为 **110/586 = 18.8%**。

- **帧集合与改动前逐帧完全一致**（丢失 0 / 新增 0 帧）：`regress` 575 帧结果
  `识别成功 492 / 无目标 28 / 可疑 21` 与改动前同值，读分 20/20、界面 5/5、关键帧闸门全过。
- 中间那版"无门限"会让个别稳定帧从"有目标"变"没目标"（`jump_028_after`/`jump_029_before`，
  比值 0.30），所以最终只在**顶面估计可信**（`顶宽 ≥ low_ratio_gate×连通域宽度`）时替换，
  退化候选保持原行为；另加"顶宽 ≤ 连通域宽度、中心须落在连通域竖直范围内"的护栏。

**同码实机 A/B（2026-10-01 12:20~12:56，1000 跳 vs 1000 跳，`tools/ab_hitrate.py`）**

| --- | --- | --- | --- |
| 分数判据命中率（权威） | 964/995 = **96.88%** | 972/999 = **97.30%** | −0.41pp，p=0.583 不显著 |

六个距离段逐一比较也全部不显著（240~300px 段：94.71% vs 95.13%，p=0.839）——
即之前怀疑的"几何瞄点伤中距离"**没有被受控实验证实**，同样，收益也没被证实。

**为什么离线"误差减半"没能变成命中率提升**：

1. 那批有白点的帧上，生产代码本来就用白点描准（`find_target` 里白点优先），
   瞄点误差≈0——**离线证据全部落在"改动不生效"的人群上**；改动真正生效的是无白点的

2. 即便瞄点中位误差真的降了 3.4px，落点误差的方差主要来自按压传递（σ≈20px），
   瞄点只占约 10% 方差 → 命中率最多动 0.3pp 量级，1000 跳的样本量根本分辨不出。

结论：**默认回到 `estimate`**（历史 3972 跳长跑用的就是它），`geometric` 保留为可选开关，
留给"能拿到无白点帧真值"的那一天再评估。这次 A/B 的价值在于**否掉了一个看似有理的改动**，
而不是又加了一个玄学参数。

### 未命中的性质：不是可修的类别偏置（2026-10-01 12:20，两轮实机 1000 跳）

几何瞄点上线后的两轮实机：**1000 跳 / 1 次死亡（#475 超时判死）/ 落地率 99.9%**，
真实命中率 97.0%（500 跳）与 96.8%（500 跳）。

## 死亡根因定位与修复（2026-10-01）

2000 跳那一轮出现 2 次死亡（第 512、1684 跳），两次都是**同一个识别缺陷**，
这次靠死亡现场帧 + `tools/inspect_frame.py` 定位到根因，不再是"随机尾部事件"：

| 现场 | 被选中的"目标" | 实际目标 | 后果 |
| --- | --- | --- | --- |
| `dead_...021438_before`（第 512 跳，得分 9145） | 影子尖 `(298,562)`，顶宽 **13px**（连通域宽 183px），距离 80.6px | 药瓶顶面 `(344,530)`，距离 136px | 按 210ms（应 356ms）→ 跳短掉落 |
| `dead_...030020_before`（第 1684 跳，得分 29662） | 影子尖 `(266,505)`，顶宽 **6px**（连通域宽 309px），距离 146px | 便利店屋顶中心，距离 265px | 按 382ms（应 692ms）→ 跳短掉落 |

两条独立成因叠在一起：

1. **影子和方块粘成一个连通域**：影子的色相/饱和度与背景几乎相同（实测影子
   `HSV=(2,25,163)` vs 背景 `(4,25,237)`，只是变暗），因此被 `block_dark_delta`
   判成方块；它和脚下的方块/目标方块相连后，连通域最上面一行就是影子的尖，
   `top_face_center` 的"左右不对称就提前返回"分支会把这个尖当成顶面，返回一个
   只有几像素宽的假顶面。
2. **淡背景上的白屋顶进不了掩码**：便利店屋顶在淡绿背景上只比背景亮 ~2、
   去饱和 ~12.5，而 `block_pale_delta=15` 抓不到它，于是连通域里没有屋顶，
   顶角只能取到影子尖。

修复（都已落地并回归验证）：

- `block_pale_delta` 15 → **10**：屋顶重新进入掩码，便利店连通域恢复到"屋顶+店身"。
- 候选分级：顶面估计宽度 < `max(12px, block_degenerate_top_ratio × 连通域宽度)`
  判为**退化估计**。前两级筛选（严格尺寸 / 放宽尺寸）只接受正常候选，
  退化候选只在最后兜底时才降级使用，并且会打印
  `警告：目标方块顶面估计退化（影子/碎片粘连），正在使用兜底候选`。

验证证据：

- `tools/ab_vision.py`：571 张历史游戏帧，**560 张完全一致，零帧丢目标**，
  仅 1 个"落地瞬间"帧的目标中心位移 15px。

### 落点误差的"真值"路线破产：`err_dot_px` / `err_src` / `aim_dot`（2026-10-01 13:10）

原计划是给 CSV 加"误差是否来自白点真值"的标记，好做灵敏 A/B 与按压传递标定。
**加完标记、拿到 35 个 `dot` 样本后，第一件事就把它证伪了**：

| 白点量出的误差 | 行数 | 游戏分数判「命中中心」 | 判「未中」 |
| --- | --- | --- | --- |
| \|err\| ≤ 12px | 10 | 10 | 0 |
| 12 < \|err\| ≤ 40px | 12 | **12** | 0 |
| \|err\| > 40px | 13 | **12** | 0 |

**12 行"误差 > 40px"的跳，游戏判的是命中中心。** 落点误差一旦真有 40px 早就摔了/不中，
所以**"落地帧中心白点"当不了真值**。机制也清楚：落地的瞬间棋子正站在白点上，
**把白点挡住了**，检测器在那个位置抓到的多是别的高光/边界（这也解释了为什么会出现
一群集中在 +45~+52px 的值）。

处理方式（不再让错误信号混进主列）：

| 列 | 含义 |
| --- | --- |
| `error_px` / `err_src` | 恢复历史口径：掩码法（`mask`）或相位相关（`flow`），**白点值不再覆盖它** |
| `err_dot_px` | 落地帧白点量出来的值，**单独存放、仅供参考**（约一半与游戏判分矛盾） |
| `aim_dot` | 本跳瞄点是否用了中心白点（1=用了，瞄点误差≈0） |

附带结论：`--calibrate` 那条标定链**再次被否**——它需要的"可信落点误差"至今不存在；
`gamma` 继续为 0 是对的。要做精度改进，只能靠"分数判据"这类二值信号 + 大样本，
或者先解决"如何拿到可信的落点真值"（例如从游戏画面外推，或用连击序列反推）。

#1371  01:33:34  landed  score=8066
#1372  01:33:38  dead    score=8098   ← 分数 8066→8098（+32 = 满连击中心命中），却判死亡

（误差测量、flow 分支、日志行）。逻辑级回归 4 例全过（现场复现 → 判落地；分数没涨/回落 → 判死）。

14 次误判**全部发生在 22:49~03:20**，即"分数增长兜底"上线之前；本次修复覆盖的是
兜底也救不了的那个变体（检测不到棋子的情况）。修完这条，死亡统计才真正等于摔跤次数。

### 第八轮：GPU 会"看别人脸色"——改成 auto 自适应（2026-10-01 10:25）

跑到一个**反直觉但很关键**的事实：GPU 不是任何时刻都更快。

| 场景 | masks() 耗时（GPU 路径） |
| --- | --- |
| 机器空闲 | **3.4 ms** |
| 有大型游戏占满 GPU（实测《坦克世界》在跑） | **66 ~ 233 ms**（20~70 倍退化，且剧烈抖动） |

原因：CUDA 内核要排队等游戏的渲染帧。若脚本固定用 GPU，别人一开游戏就会从"很快"变成"极慢"。

所以 `masks_backend` 默认改为 **`auto`**，规则是：

1. 启动时 gpu / simd **各测 5 次取中位**，只有 `gpu×1.5 ≤ simd`（明显更快）才用 GPU；
2. 每 300 次掩码**复测一次**（中途开游戏也能发现）；
3. 运行期用**滚动中位**监测：GPU 一旦慢过 `max(2×SIMD基准, 30ms)` 就立刻切回 SIMD 并打日志。

验证（当下 GPU 正被游戏占满）：`掩码后端自动选择：simd（实测 simd 19.00ms、gpu 232.81ms）`，
且输出与 SIMD 路径**逐像素一致**（piece/block 差异均为 0）。手机器空闲时它会自动选 GPU。

| `press_duration_max_ms` | 按压时长上限 | 1500（443.7px×2.61=1158ms） |
| `axis_max_cross_ratio` | 目标向量允许偏离等距轴向的程度 | 0.45（棋子站在便利店前部时会到 0.35） |
| `block_color_delta` / `block_pale_delta` | 区分方块与背景阴影的色距/去饱和阈值 | 45 / **10**（15→10：淡背景上的白屋顶能被抓到了） |
| `block_degenerate_top_ratio` | 顶面估计宽度低于该比例×连通域宽度 = 退化估计（影子尖） | 0.10（前两级筛选拒绝，仅兜底可用） |
| `block_bright_delta` | 比背景亮且不比背景饱和 = 浅色方块（0 = 关闭） | 0（备而未用） |
| `low_ratio_gate` / `low_ratio_trim_ratio` | 顶面/宽度低于 gate 判为"粘连块"；trim>0 时对该类按比例缩短按压 | 0.45 / 0（实验开关，默认关） |
| `piece_template_min_score` | 棋子与 `templates/piece.png` 的最低相关度 | 0.45 |
| `piece_scan_min_score` | 多模板扫描找棋子的最低相关度（跨皮肤用） | 0.55 |
| `modal_dark_threshold` | 中央暗像素占比判弹窗的灰度阈值 | 110（占比 >0.85 才判弹窗） |
| `detect_retry_limit` | 识别连续失败的重试次数（期间绝不盲按） | 40（≈20 秒） |

启动时日志会打印**当前生效的全部阈值**，便于发现“改了代码但被 config.json 旧值覆盖”的问题。
